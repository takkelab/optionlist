# メトリクスと目標値

[SPEC.md](../../SPEC.md) の一部。**この章はレビュー対象**。

- **CI で判定する目標値は `metrics.config.json` に一元管理**し（§5・§6・§8 の目標値は CI で判定しないので入れない）、CI のチェックスクリプトとこの章はこれを参照する。目標値を変えるときはこのファイルと本章を同じ PR で直し、理由を docs/decisions/ に残す（process.md §3）
- 判定の列
  - **CI 失敗**: 目標を割ったら CI を失敗させる（マージしない）
  - **CI 警告**: CI のサマリーに出すが失敗にはしない
  - **観測**: 記録してベースラインを取る。目標値はベースラインを見て決める
- 計測結果は CI のジョブサマリーと `metrics-report.json`（CI の成果物）に出す。ローカルでは `npm run metrics:check` で同じ判定を行う

## 1. 性能テスト用のデータ量
性能の目標値は、次のデータを入れた状態で、「測る人」として API を呼んで測る（1 人が毎日使って数年分を想定し、余裕を持たせた量。そのうえで、ほかの人の行が混ざっていてもインデックスで絞れることを確かめるため、ほかの人も入れる。docs/decisions/0034）。

| テーブル | 測る人 | ほかの人 |
|----------|--------|----------|
| users | 1 | 9,999（うち 49 人がデータを持つ。残りは項目のない人） |
| options | 1,000（pending 500 / completed 500。半分に予定日） | 49 人 × 1,000（同じ内訳） |
| achievements | 5,000（3 件に 1 件に写真の名前） | 49 人 × 5,000 |
| events | —（誰のものでもない）100,000 | — |

## 4. backend の性能（統合テストで計測、§1 のデータで）
| 指標 | 目標値 | 計測方法 | 判定 |
|------|--------|----------|------|
| 読み取り API の応答時間 p95 | 50ms 以内 | 各 API を 100 回呼んで計測 | CI 失敗 |
| 書き込み API の応答時間 p95 | 80ms 以内 | 同上 | CI 失敗 |
| 画像のアップロード（1MB）の応答時間 p95 | 300ms 以内（sharp で作り直す時間を含む。R5 の CI で 53.2ms〈1MB のノイズの JPEG〉。docs/decisions/0037・0051） | 20 回呼んで計測 | CI 失敗 |
| SQL 1 本あたりの実行時間 p95 | 10ms 以内 | pg のラッパーで計測 | CI 失敗 |
| 1 リクエストあたりの SQL の本数 | 一覧・詳細は 3 本以内 | 同上（N+1 を防ぐ）。トランザクションの `BEGIN`・`COMMIT`、`set_config`（RLS。data.md §4）、セッションの `auth_find_user` と 1 日 1 回の `last_seen_at` の更新（api.md §6）は数えない | CI 失敗 |
| 主要クエリのフルテーブルスキャン | 0 件 | `SET LOCAL enable_seqscan = off` の中で `EXPLAIN (FORMAT JSON)` の `Seq Scan` を検出する（索引で読めないものだけを数える。docs/decisions/0047。`app.user_id` を測る人にして流す）。マスターデータの表（themes・tags・suggestions・suggestion_tags。提案の一覧の API が全部読む）は数えない（docs/decisions/0021） | CI 失敗 |
| 連続 1,000 リクエスト後のヒープ増加 | 10MB 以内（GC 後） | `--expose-gc` で前後の `heapUsed` を比較 | CI 失敗 |
| 連続 1,000 リクエスト中の RSS 最大値 | 200MB 以内 | `process.memoryUsage()` | CI 失敗 |

CI のランナーは性能がぶれるので、目標を割った場合は 1 回だけ測り直し、2 回とも割ったら失敗にする ※仮決め

## 5. 実行時メトリクス（Cloud Monitoring と `/api/metrics`）
アプリを使っている間の状態を見るための指標。本番と確認用では、Cloud Run の標準の指標（応答時間・リクエスト数・台数・メモリ）と、JSON のログ（`kind`）から作るログベースの指標を Cloud Monitoring で見る。prom-client の `/api/metrics` は残すが、トークンがないと 404（docs/decisions/0042）。

| メトリクス | 内容 | 目標値 |
|------------|------|--------|
| `http_request_duration_seconds` | ルート・ステータス別の応答時間（ヒストグラム） | p95 100ms 以内 |
| `http_requests_total` | ルート・ステータス別のリクエスト数 | 5xx の割合 1% 未満 |
| `db_query_duration_seconds` | SQL の実行時間（ヒストグラム） | p95 10ms 以内 |
| `unhandled_errors_total` | 共通エラーハンドラに届いた想定外のエラー数 | 0 |
| `orphan_file_errors_total` | 画像ファイルの削除に失敗した数 | 0 |
| `process_resident_memory_bytes` ほか | prom-client の標準メトリクス | RSS 200MB 以内 |

- この節の目標値は CI では判定しない。Cloud Monitoring のダッシュボードで週ごとに確認する（`metrics:usage` には出さない）。すぐ気づくべきものは §8 のアラートにする
- Cloud Run は最小 0 台なので、しばらく使われなかったあとの最初のリクエストは起動を待つ（1〜3 秒）。起動にかかった時間（Cloud Run の起動の指標）は観測し、p95 を週ごとに見る（docs/decisions/0035）

## 6. 利用状況（集計のビューから。docs/decisions/0043）
`npm run metrics:usage` で直近 1 週間と直近 4 週間（週あたりに割った値）を表示する。画面の閲覧・提案の閲覧は記録しない（docs/decisions/0031）。
読むのは `ol_metrics` ロールで、件数と日数だけを返す集計のビュー（`usage_*`。data.md §4）だけ。タイトル・写真・個々の人の行は読まない。接続先は `METRICS_DATABASE_URL`（本番は Cloud SQL Auth Proxy 越し）。
この節の目標値は CI で判定しないので `metrics.config.json` には入れず、`metrics:usage` が ✓ / ✗ を付ける（`scripts/lib/usage-report.ts`）。

「使った人」は、期間内に `last_seen_at` を書いた人（その期間に 1 回以上開いて、アカウントがある人）。

| 指標 | 定義 | 目標値 |
|------|------|--------|
| **達成した人の割合**（最重要） | 使った人のうち、期間内に 1 回以上 `achievements` がある人の割合 | 観測（一般公開から 4 週でベースラインを取り、目標値を決める。「新しい体験への一歩」を実際に踏み出せているか） |
| 1 人あたりの達成数 | 期間内の `achievements` の件数 ÷ 使った人 | 観測 |
| 使った人の数 | 上の定義 | 観測 |
| 続けて使った人の割合 | 4 週前の週に新しくできたアカウントのうち、その後の 3 週のどこかでも使った人の割合 | 観測（想定ユーザーが続けて開いているか） |
| 提案から追加した件数 | 期間内に作った option のうち `suggestion_id` があるもの（消した項目は数えない）÷ 使った人 | 観測（少ないまま続いたら提案の中身を見直す） |
| 追加から初回達成までの日数 | 期間内に初めて達成した option の、作成から最初の achievement までの日数の中央値 | 観測 |
| やりたいリストの滞留 | 使った人ごとの「今の pending のうち作成から 90 日以上たったものの件数」の中央値（期間によらない） | 観測 |
| frontend のエラー数 | `client_error` の件数（多いメッセージを 3 つまで添える）÷ 使った人 × 100 | 使った人 100 人あたり 5 件以下 / 週 ※仮決め |

## 7. AI を使った開発のコスト
実装ステップごとに `docs/metrics/ai-usage.md` に記録する。

| 指標 | 計測方法 | 目標値 |
|------|----------|--------|
| 使用量 | Claude の使用量表示（5 時間枠・週の使用率）を、ステップの開始時と PR マージ時に控えて差を取る | 観測（ステップ 1〜2 でベースラインを取る） |
| 所要時間 | ステップの開始から PR マージまで | 観測 |
| AI レビューの指摘件数 | reviewer サブエージェント・PR レビューの指摘数 | 観測 |
| CI の失敗回数 | PR ごとの失敗回数 | 観測 |
| AI が詰まった件数 | `docs/harness/incidents.md` の件数（process.md §2） | 観測 |
| 再発防止策の内訳 | 環境 / lint・テスト / スクリプト / スキル / CLAUDE.md の件数 | 観測（環境・lint・テストの割合を高く保つ） |
| 同じ原因での再発 | 対策を入れたあとに同じ原因で詰まった件数 | 0 件 |

## 8. 運用（本番。docs/decisions/0040〜0042）
CI では判定しない。アラートは Cloud Monitoring からメールで受け取り、訓練の結果は `docs/ops/` に書く。

| 指標 | 目標値 | 見方 |
|------|--------|------|
| 外からの死活監視（`/api/health`、5 分ごと） | 2 回続けて失敗しない | アラート |
| 5xx の割合（5 分間） | 5% 以下 | アラート |
| `kind: unhandled_error`・`kind: orphan_file_error` のログ | 0 件 | 1 件でもアラート |
| `client_error`（1 時間） | 50 件以下 | アラート（1 時間ごとのジョブが数えてログに出す） |
| 削除のジョブ（data.md §5） | 毎日成功する | 失敗か、26 時間動いていなければアラート。消した件数は `kind: cleanup_result` のログで見る |
| バックアップの書き出し（data.md §6） | 毎週成功する | 失敗か、8 日動いていなければアラート |
| 復旧の訓練（`npm run ops:restore-drill -- production`） | 四半期に 1 回（最初は公開の 1 段目）。その場で取ったバックアップを新しい一時的なインスタンスに戻し、バックアップの前後に残っていた本番の利用者の表の ID がすべて戻り（それが空なら失敗）、前後で写真が変わっていない達成で「行があるのに写真がない」が 0 件（data.md §6） | `docs/ops/restore-drills.md` に書く |
| 月の費用 | 3,000 円以内（docs/decisions/0035） | 予算の 50・90・100% でアラート |
| 中身を見た回数 | 障害対応のときだけ | `docs/ops/data-access.md` に日付と理由を書く（docs/decisions/0043） |
