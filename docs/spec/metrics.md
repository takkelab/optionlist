# メトリクスと目標値

[SPEC.md](../../SPEC.md) の一部。**この章はレビュー対象**。

- **CI で判定する目標値は `metrics.config.json` に一元管理**し（§5・§6 の目標値は CI で判定しないので入れない）、CI のチェックスクリプトとこの章はこれを参照する。目標値を変えるときはこのファイルと本章を同じ PR で直し、理由を docs/decisions/ に残す（process.md §3）
- 判定の列
  - **CI 失敗**: 目標を割ったら CI を失敗させる（マージしない）
  - **CI 警告**: CI のサマリーに出すが失敗にはしない
  - **観測**: 記録してベースラインを取る。目標値はベースラインを見て決める
- 計測結果は CI のジョブサマリーと `metrics-report.json`（CI の成果物）に出す。ローカルでは `npm run metrics:check` で同じ判定を行う

## 1. 性能テスト用のデータ量
性能の目標値は、次のデータを入れた状態で測る（毎日使って数年分を想定し、余裕を持たせた量）。

| テーブル | 件数 |
|----------|------|
| options | 1,000（pending 500 / completed 500。半分に予定日） |
| achievements | 5,000 |
| events | 100,000 |

## 4. backend の性能（統合テストで計測、§1 のデータで）
| 指標 | 目標値 | 計測方法 | 判定 |
|------|--------|----------|------|
| 読み取り API の応答時間 p95 | 50ms 以内 | 各 API を 100 回呼んで計測 | CI 失敗 |
| 書き込み API の応答時間 p95 | 80ms 以内 | 同上 | CI 失敗 |
| 画像のアップロード（1MB）の応答時間 p95 | 300ms 以内 | 20 回呼んで計測 | CI 失敗 |
| SQL 1 本あたりの実行時間 p95 | 10ms 以内 | mysql2 のラッパーで計測 | CI 失敗 |
| 1 リクエストあたりの SQL の本数 | 一覧・詳細は 3 本以内 | 同上（N+1 を防ぐ） | CI 失敗 |
| 主要クエリのフルテーブルスキャン | 0 件 | `EXPLAIN` の `type = ALL` を検出。マスターデータの表（themes・tags・suggestions・suggestion_tags。提案の一覧の API が全部読む）は数えない（docs/decisions/0021） | CI 失敗 |
| 連続 1,000 リクエスト後のヒープ増加 | 10MB 以内（GC 後） | `--expose-gc` で前後の `heapUsed` を比較 | CI 失敗 |
| 連続 1,000 リクエスト中の RSS 最大値 | 200MB 以内 | `process.memoryUsage()` | CI 失敗 |

CI のランナーは性能がぶれるので、目標を割った場合は 1 回だけ測り直し、2 回とも割ったら失敗にする ※仮決め

## 5. 実行時メトリクス（`/api/metrics` で公開）
アプリを使っている間の状態を見るための指標。prom-client で公開する。

| メトリクス | 内容 | 目標値 |
|------------|------|--------|
| `http_request_duration_seconds` | ルート・ステータス別の応答時間（ヒストグラム） | p95 100ms 以内 |
| `http_requests_total` | ルート・ステータス別のリクエスト数 | 5xx の割合 1% 未満 |
| `db_query_duration_seconds` | SQL の実行時間（ヒストグラム） | p95 10ms 以内 |
| `unhandled_errors_total` | 共通エラーハンドラに届いた想定外のエラー数 | 0 |
| `orphan_file_errors_total` | 画像ファイルの削除に失敗した数 | 0 |
| `process_resident_memory_bytes` ほか | prom-client の標準メトリクス | RSS 200MB 以内 |

- この節の目標値は自動では判定しない。`/api/metrics` を見て週ごとに確認する（`metrics:usage` には出さない）

## 6. 利用状況（events と既存テーブルから集計）
`npm run metrics:usage` で直近 1 週間と直近 4 週間（週あたりに割った値）を表示する。画面の閲覧・提案の閲覧は記録しない（docs/decisions/0031）。
この節の目標値は CI で判定しないので `metrics.config.json` には入れず、`metrics:usage` が ✓ / ✗ を付ける（`scripts/lib/usage-report.ts`）。

| 指標 | 定義 | 目標値 |
|------|------|--------|
| **週あたりの達成数**（最重要） | `achievements` の週ごとの件数 | 1 件以上（「新しい体験への一歩」を実際に踏み出せているか） |
| 提案から追加した件数 | 期間内に作った option のうち `suggestion_id` があるもの（消した項目は数えない） | 観測（少ないまま続いたら提案の中身を見直す） |
| 追加から初回達成までの日数 | 期間内に初めて達成した option の、作成から最初の achievement までの日数の中央値 | 観測 |
| やりたいリストの滞留 | 今の pending のうち、作成から 90 日以上たったものの件数（期間によらない） | 観測 |
| frontend のエラー数 | `client_error` の件数（多いメッセージを 3 つまで添える） | 0 件 / 週 |

## 7. AI を使った開発のコスト
実装ステップごとに `docs/metrics/ai-usage.md` に記録する。

| 指標 | 計測方法 | 目標値 |
|------|----------|--------|
| 使用量 | Claude の使用量表示（5 時間枠・週の使用率）を、ステップの開始時と PR マージ時に控えて差を取る | 観測（ステップ 1〜2 でベースラインを取る） |
| 所要時間 | ステップの開始から PR マージまで | 観測 |
| AI レビューの指摘件数 | reviewer サブエージェント・PR レビューの指摘数 | 観測 |
| CI の失敗回数 | PR ごとの失敗回数 | 観測 |
| AI が詰まった件数 | `docs/harness/incidents.md` の件数（process.md §2） | 観測 |
| 再発防止策の内訳 | 環境 / lint・テスト / スクリプト / スキル / CLAUDE.md の件数 | 観測（環境・lint・テストの割合を高く保つ） |
| 同じ原因での再発 | 対策を入れたあとに同じ原因で詰まった件数 | 0 件 |
