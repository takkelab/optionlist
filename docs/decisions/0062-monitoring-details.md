# 0062 監視の細部（client_error はジョブでなく受け取るたびのログで数え、確認用は死活監視だけ、予算はクレジットを引く前の金額で見る）

- 日付: 2026-11-12
- 状態: 確定（しきい値は 0042 のとおり、使って見直す）
- 対象: metrics.md §8、architecture.md §4.1・§4.3、process.md §5 の R10c、docs/decisions/0042

## 決めたこと
- `client_error` の 1 時間の件数は、1 時間ごとのジョブでは数えない（0042 を変える）。backend が `POST /api/events` で `client_error` を保存したら、件数だけの 1 行（`kind: client_error_received`、`counts.clientErrors`。メッセージ・画面は出さない）をログに出す。ログベースの指標 `optionlist_production_client_errors`（分布。`counts.clientErrors` を取り出す）の 1 時間の合計が 50 を超えたらアラートにする
- アラートは本番に metrics.md §8 のすべてを付け、確認用には死活監視だけを付ける
- 通知先は、運営者のメール 1 つ（表示名「optionlist 運営者のメール」。確認用・本番で共用）。アドレスはリポジトリ（公開）に書かず、`infra:setup`・`infra:check` を流したときに gcloud にログインしているアカウント（`gcloud config get-value account`）を使う。`infra:check` は、通知先のアドレスがそのアカウントと同じかを確かめる（画面にはアドレスを出さない）
- 通知先・死活監視・アラートのポリシー・ログの指標・予算は、gcloud ではなく REST API で作る（`infra/lib/google-api.ts`）。通知先は gcloud では beta にしかなく、ほかもポリシーの JSON をそのまま渡せるほうが、作る側と確かめる側で同じ定義（`infra/monitoring.ts`）を使える。どれも表示名で探して、あれば置き換え、なければ作る
- 死活監視は、`/api/health` を 5 分ごとに 3 つの地域（アジア太平洋・ヨーロッパ・米国オレゴン。3 つが最小）から叩き、本文に `"status":"ok"` があるかも見る（2xx 以外を成功に数える設定は付けない）。アラートは PromQL で、「直近 9 分に成功が 1 つもない地域」が 2 つ以上のとき（`count(max_over_time(check_passed[9m]) == 0) > 1`）。点検は 5 分ごとなので、9 分ずっと失敗なら少なくとも 2 回続けて失敗している。最初は「失敗した地域が 2 つ以上の状態が 9 分続く」しきい値の条件（5 分の整列）にしたが、指標の点は 1 分ほどの間隔で書かれ、整列の窓と点検の時刻のずれで続いた時間がリセットされうるとレビューで分かり、変えた
- 死活監視・5xx の割合・`client_error`・ジョブは PromQL の条件にする。PromQL の条件は 1 つのポリシーに 1 つしか置けないので、ジョブは「失敗」と「止まり」を別のポリシーにする（本番は 8 つのポリシー、条件は 8 つ。確認用は 1 つ）
  - ジョブの失敗: Cloud Run の `job/completed_execution_count` の `result="failed"` が直近 1 時間に 1 以上（この指標は実行が終わったときに 1 点だけ書かれるが、Cloud Monitoring の `increase(...[1h])` は点が 1 つでも 1 を返し、1 時間を過ぎると消えることを、確認用の削除のジョブの成功で確かめた）。`cleanup_failed`・`backup_failed` のログではなく実行の結果で見るので、時間切れやメモリ不足でログを出せずに落ちたものも拾う
  - ジョブの止まり: `result="succeeded"` が削除のジョブは 26 時間、書き出しは 8 日ない（`absent_over_time`）。25 時間を超えて振り返る式は、続く時間を 0、評価の間隔を 26 時間なら 5 分以上・8 日なら 1 時間以上にしなければならない（API が断る）ので、5 分・1 時間にする
- `unhandled_error`・`orphan_file_error`・`account_cleanup_error`（引き継ぐ前のアカウントを消せず、残った。api.md の引き継ぎ）は、ログに一致したら鳴る条件。本番のサービスと、本番の削除のジョブ（写真のファイルを消せなかったときに `orphan_file_error` を出す。0059）のログを見る。同じ原因で何度も出るので、通知は 5 分に 1 回まで、30 分出なければ閉じる。`db_pool_error`（使っていない接続が切れた）は pg がつなぎ直すので拾わない
- 予算は請求先アカウントに作り（置き換えるときは updateMask で決めた項目を名指しする。ないと既定値に戻せず、`budgetFilter` は丸ごとだと断られるので中の項目を名指しする）、対象をこのプロジェクトに絞る。月 3,000 円の 50・90・100%（今の使い方の金額）で、運営者のメールと、請求先アカウントの管理者への既定のメールの両方に送る。金額は**クレジットを引く前**で数える（無料トライアルの間も、使い方が上限に近いかが分かるように）。請求先アカウントの ID もリポジトリに書かず、`gcloud billing projects describe` で読む

## 理由
- 1 時間ごとのジョブにすると、Cloud Run Job・Scheduler（請求先アカウントで無料なのは 3 つまで。4 つ目になる）・サービスアカウントのほかに、`events` を数えられるロールが要る。`ol_metrics` の接続先は誰にも読ませない決まり（0060）で流用できず、新しいロールか集計のビューを足すことになる。受け取るたびにログに出せば、Cloud Logging と Cloud Monitoring だけで数えられ、増えるものはログの 1 行だけ。1 回の送信に最大 50 件入るので、行の数ではなく `counts.clientErrors` の合計で数える
- 確認用はデプロイのたびに壊れることがあり、全部のアラートを付けるとメールが増えすぎて見なくなる（0042 の「気づくべきことだけ」）。死活監視だけは、完了の条件（わざと失敗させてメールが届くか）を本番を壊さずに確かめるために付ける
- アラートの条件は 2026-05-01 から 1 つ月 $0.10 かかる（ほかに、条件の問い合わせが返す時系列 100 万件あたり $0.35）。9 つで月 140 円ほどで、月 3,000 円（0035）の中に収まる。死活監視とログの指標は無料枠の中
- 今の請求は月 1,800〜2,000 円（0058）なので、50%（1,500 円）のアラートは毎月の後半に鳴る見込み。鳴ること自体で、予算のアラートが届くことを毎月確かめられる。クレジットを引いた後で数えると、トライアルが終わる 2027-02-08 まで 0 円のままで、鳴るかを確かめられない

## 影響
- `infra:setup` の表示（dry-run の本文と URL）は、メールアドレスと請求先アカウントの ID を伏せる
- 確認用で死活監視のアラートを確かめるときは、確認用のサービスから公開の呼び出し権限を外して `/api/health` を 403 にし、メールが届いたら戻す（`gcloud run services remove-iam-policy-binding optionlist-staging --region asia-northeast1 --member=allUsers --role=roles/run.invoker` → 届いたら `add-iam-policy-binding` で同じものを戻し、`npm run infra:check -- staging`）
- 死活監視が 5 分ごとに 3 つの地域から叩くので、確認用・本番とも 1 日に 860 回ほどのリクエストが増える。`/api/health` は DB に触れず、Cookie も作らない。5xx の割合の分母にも入る
- 新しい `kind` を足すときは、アラートで拾うかを決めて `infra/monitoring.ts` に書く
