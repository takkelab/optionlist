# 0060 R10 を 3 つに分け、利用状況のビューは「今日を含む直近の期間（日本時間の 0 時から）」で数える

- 日付: 2026-11-11
- 状態: 確定
- 対象: process.md §5、metrics.md §6、data.md §4、architecture.md §4.2

## 決めたこと
- R10（バックアップ・監視・利用状況）を、R10a 利用状況 → R10b バックアップ → R10c 監視 の 3 つの PR に分ける。完了の条件もそれぞれに振り分ける（R10c のアラートは R10b の書き出しの Job を見るので、この順にする）。アラートの通知先は運営者の Claude のアカウントのメールアドレスにする（R10c）
- 集計のビュー（`usage_periods`・`usage_retention`・`usage_stale_pending`・`usage_client_error_messages`）は、今日（日本時間）を含む直近の 7 日・28 日で数える。始まりは 6 日前・27 日前の日本時間の 0 時、終わりは読んだ時点の `now()`
- `client_error` は受け取った時刻（`received_at`）で数える。メッセージのない行は「（メッセージなし）」と出す
- 4 週間の列は件数を 4 で割って週あたりにし、割合・中央値・使った人の数は割らない。使った人が 0 なら割り算の値を `-` にして判定しない
- 「続けて使った人」は、作成が日本時間で 27〜21 日前の 7 日のアカウントのうち、`last_seen_at` が 20 日前の 0 時より後の人。滞留の「使った人」は直近 4 週間（上と同じ 28 日）に使った人で、「90 日以上」は 24 時間 × 90 でちょうど 90 日を含む
- 多い `client_error` のメッセージは、ビューの中で 3 つに絞る
- 確認用・本番の利用状況は `npm run metrics:usage -- --env <env>` で見る。Cloud SQL Auth Proxy を起動し、秘密の値 `optionlist-<env>-metrics-database-url`（`npm run infra:setup -- db <env>` が作る）のパスワードで `ol_metrics_<env>` としてつなぐ。この秘密の値には誰にも読む権限を付けない（読むのはプロジェクトの持ち主だけ。`infra:check` で確かめる）
- 今のコードに残っていた「週あたりの達成数 1 件以上」の目標は消す（0043 で 1 人あたりの指標に変え、metrics.md には残っていない）

## 理由
- 量が R9 の 3 倍ほどあり、1 つの PR ではレビューで見落としやすい。ステップ 1 を 1a〜1c に分けたのと同じ考え方
- ビューは引数を取れない。期間を受け取る関数（`SECURITY DEFINER`）にする案もあるが、関数は `ol_app` だけが実行できる決まり（testing.md §7）の例外が増える。`metrics:usage` が見るのはいつも「今まで」の期間なので、`now()` で区切れば足りる。日ごとの集計を返すビューは、期間をまたいだ「使った人」の重なりを数えられない（個々の人の行を返すことになる）
- `last_seen_at` は、最後に使った日（日本時間）の最初のリクエストで 1 日 1 回だけ書く（api.md §6）。期間の始まりを日の途中（`now() - 7 日`）にすると、始まりの日に区切りより前と後の両方で使った人は、`last_seen_at` が区切りより前のままなので「使った人」から漏れる。その人の達成は件数に入るので、1 人あたりの値の分母と分子が食い違う。始まりを日本時間の 0 時にそろえれば、`last_seen_at` が期間内にあるかで「期間内に使った」がちょうど数えられる。続けて使った人も、あとの 3 週が今で終わり 0 時から始まるので同じ（最初の計画は 24 時間 × 日数だったが、レビューでこのずれが見つかり、0 時にそろえた）
- `occurred_at` は端末の時計で、ずれていると期間の外に落ちる。削除のジョブ（data.md §5）と同じく、backend の時計の `received_at` で数える
- `METRICS_DATABASE_URL=… npm run …` は PowerShell では書けない。Proxy の起動とパスワードの読み出しは `infra:check` と同じ形なので、そのまま使う
- ビューで 3 つに絞れば、エラーのメッセージ（frontend が送る文字列）を運営者が見る量も最小になる

## 影響
- ビューは読むたびに表を数えるので、利用者が増えて遅くなったら、索引か集計の表を考える（今は性能テストの対象にしない。`metrics:usage` は手で週に 1 回流すだけ）
- テストは、行を入れる接続と読む接続で `now()` がずれるので、境目を 1 分の内・外で確かめる（時刻は DB の時計で「日本時間の n 日前の 0 時 ± 1 分」「今から m 分前」として入れる）
- 前からある手元の `backend/.env`・`backend/.env.test` には `METRICS_DATABASE_URL` を書き足し、`db:roles`・`db:roles:test` を流し直す
