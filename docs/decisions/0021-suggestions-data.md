# 0021 提案のマスターデータの書き方と更新のしかた、フルテーブルスキャンの扱い（ステップ 7a）

- 日付: 2026-11-03
- 状態: 確定（件数・季節の割合は使ってみて見直す）
- 対象: data.md §2、metrics.md §4、testing.md §1、SPEC.md（版・§3）

## 決めたこと
- 提案は 95 件・テーマ 10 個・タグ 39 個で始める。季節つきは 49 件で、**どの月にも今月のおすすめが 5 件以上**ある（マイグレーションテストで確かめる）
- 豆知識には、年で変わる日付（「今年の極大は 12/14」など）を書かない。月が変わると今月のおすすめが入れ替わるのは、季節の列と端末の日付だけで行う（アプリで中身を作ったり書き換えたりはしない）
- AI への相談文は、提案ごとに質問を用意せず、今の共通の相談文（screens.md §2）のままにする。聞きたいことはダイアログでその場で書き足す
- 提案の追加・書き直しは、新しいマイグレーション（INSERT / UPDATE）で行う。ID は変えず、提案は消さない（中身が別物になるなら新しい ID で足す）
- metrics.md §4 のフルテーブルスキャンでは、マスターデータの表（themes・tags・suggestions・suggestion_tags）を数えない。options など、それ以外の表は今までどおり数える

## 理由
- 見本 10 件をユーザーと読み合わせた。ユーザーの希望は「季節感を出して、月ごとに自動で入れ替わってほしい」だった。季節の月を持たせておけば、12 か月分を先に用意するだけで入れ替わる
- 相談文に提案ごとの質問を足す案も出したが、ユーザーは共通の文で足りると判断した（聞きたいことは人によって違い、その場で直せる）
- 一覧の API は、固定の 100 件前後を全部返す（api.md §2）。実際の EXPLAIN では themes・suggestions が `type = ALL`（10 行・95 行）だった。インデックスを使わせて `type = index` にしても全部読むことは変わらず、指標をごまかすだけなので、表の名前で外す。性能用データ（options 1,000 件）を入れた状態では、提案の SQL から options への結合はインデックスを使い、フルテーブルスキャンは 0 件だった
- 提案を消すと、そこから追加した option のつながり（`suggestion_id`）を外す必要がある。消さずに足していけば、既存のつながりを壊さない

## 影響
- マイグレーション: `20261103062436_restructure_suggestions.sql`（表の作り直し）、`20261103062438_insert_explore_suggestions.sql`（中身）
- 性能テスト: EXPLAIN の別名を表名に戻して判定する（`backend/tests/fakes/FullScanFinder.ts`）。提案の一覧・1 件を読み取りの計測に足した
- SPEC.md §3 から「提案の一覧の API のフルテーブルスキャンの扱い」を消した
