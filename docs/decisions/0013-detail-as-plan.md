# 0013 詳細画面をチャットから「プラン」型にする（予定日・1 枚のメモ・リンク）（ステップ 5）

- 日付: 2026-11-01
- 状態: 一部取り消し（詳細画面・メモ・リンクは 0014 でやめた。予定日＝準備中、予定日だけをカードに出す、は残る）
- 対象: SPEC.md §2・§3、screens.md §1・§2・§3、data.md §2・§3、api.md §2〜§5、metrics.md §1・§3・§4、testing.md §2・§5、process.md §4

## 決めたこと
- 詳細画面のタイムライン（LINE の KEEP メモ風に、メモを時系列で積む形）をやめ、上から「予定日」「メモ」「リンク」を並べる
- 予定日は日付だけ（`options.planned_on DATE`）。予定日が入っている項目を「準備中」とみなし、状態（status）は増やさない
- メモは 1 項目に 1 枚（`options.memo TEXT`、10,000 文字まで ※仮決め）で、何度でも書き直せる。本文中の URL はリンクにする
- URL は専用の欄（`links` テーブル）にし、何個でも貼れる。ラベルは手で付ける（任意）。ページタイトルの自動取得は今回は入れない
- 一覧のカードには予定日を出すだけで、並び順は変えない
- 使っていない notes テーブルはマイグレーションで消す。画像をどこに付けるかはステップ 8 の始めに決める（SPEC.md §3。今の案は 🎉 のときの写真）
- PATCH `/api/options/:id` は `OptionDetail` を返す（メモの前後の空白を除いたあとの値を frontend がそのまま使えるように）
- metrics.md §3 のタップ領域から、文章の中のリンク（メモの本文の URL、`data-inline-link`）を外した。行の高さのまま折り返して読むもので、44px にすると本文が読みにくくなる（WCAG 2.5.8 の「文中」の例外と同じ考え）。同じ URL はリンクの欄に貼れば 44px の行で開ける。測る対象に textarea を足した
- metrics.md §4 の画像の指標の名前を「画像付きメモ投稿」から「画像のアップロード」にした（`image-note-p95` → `image-upload-p95`。目標値は変えない）

## 理由
- このアプリの詳細画面は、「やってみたいこと」の空想を具体化する場所（ユーザーの判断）。具体化に要るのは「いつ・何をするか」の**今の状態**が一目で見えることと、書き直せることで、書いた順に流れて上に消えていくチャットとは合わない。チャットのよさ（気軽に書き足せる、やった後の記録が残る）は、やる前よりやった後に向いている
- メモを「1 枚 ＋ 時系列」の両方にする案は、どちらに書くか迷うので採らなかった
- URL は 1 項目に何個も貼る（ユーザーの見込み）。メモの本文に混ぜると本文が URL で埋まって読みにくいので分けた。それでもメモに書いた URL は開けるようにして、貼り分けを間違えても困らないようにした
- 予定日以外の欄（場所・予算・持ち物など）は作らず、まずメモに書く。毎回メモに書いているものが出てきたら欄にする
- 予定日の近い順に並べると、ステップ 9 のドラッグ＆ドロップの並び替えとぶつかる
- タイトルの自動取得は、外部へのアクセス・タイムアウト・失敗時の扱いが増え、ローカルだけで動かす前提（SPEC.md §1.2）とも合わせて考える必要があるので後にした
- notes はステップ 5 で使い始める予定のテーブルで、まだデータがない。残すと「どこにメモがあるのか」が二重になる

## 影響
- マイグレーション 3 本（options に列を足す、links を作る、notes を消す）。性能用データは notes の代わりに links 20,000 件と、options のメモ・予定日を入れる
- API: `POST /api/options/:id/notes` をなくし、`POST /api/options/:id/links`・`PATCH /api/links/:id`・`DELETE /api/links/:id` を足した。`Option` に `plannedOn`、`OptionDetail` に `memo`・`links` を足し、`Note` 型を消した
- 詳細画面は開いたときに一番下までスクロールしないので、PR #9 で残した「一番下までスクロールするとヘッダーが隠れる」は起きなくなった
