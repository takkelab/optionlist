# 0041 自動バックアップ・時点復旧・週 1 の書き出しに加えて、四半期ごとに戻せるかを確かめる

- 日付: 2026-11-08
- 状態: 確定
- 対象: data.md §6、metrics.md §8、process.md §5

## 決めたこと
- Cloud SQL: 毎日の自動バックアップを 7 日分残し、時点復旧（7 日以内の好きな時点に戻せる）を有効にする。インスタンスを消してもバックアップを残す設定にし、削除保護もかける
- 週 1 回（日曜 5 時）、Cloud Run Job が `ol_migrator` で `pg_dump --enable-row-security` を流し、`optionlist_production` の DB だけを別の入れ物（`optionlist-backups`。保持の期限は 35 日）に書き出す（`--enable-row-security` がないと RLS のある表で止まる）
- 写真の入れ物は、消したものを 7 日間戻せる設定（soft delete）にする
- 四半期に 1 回、`npm run ops:restore-drill -- production` で復旧の訓練をする。最新の自動バックアップを**新しい一時的なインスタンス**（`restore-drill-<日時>`。消した名前はしばらく使い直せないので毎回変える）に戻し、`ol_migrator` で `optionlist_production` の利用者の表（users・options・achievements）の件数と「行と写真の食い違い」（行があるのに写真がない・写真があるのに行がない）を数えて、本番と比べる。本番の利用者の表が 0 件なら失敗にする（数え方の誤りで 0 件どうしが一致するのを防ぐ。マスターデータは数えない）。結果を `docs/ops/restore-drills.md` に書き、終わったら一時的なインスタンスを消す
- 本番に利用者の行が入る前（R10）は、同じ手順を確認用（`-- staging`）で行って仕組みを確かめる。本番での最初の訓練は、公開の 1 段目（0045）で行う
- 自動バックアップと時点復旧はインスタンス全体が単位で、インスタンスは確認用・ほかのアプリと共用している。そのため、戻すときも共用のインスタンスをその場で巻き戻さず、新しいインスタンスに戻してから `optionlist_production` の DB だけを入れ直す

## 理由
- 自動バックアップは、初期設定ではインスタンスと一緒に消える。共用のインスタンス（0035）を操作ミスで消すと、全部のアプリを失う
- DB と写真は別々に戻るので、戻した時点がずれると、片方だけが残る。訓練で、この食い違いが何件出るか、そのときどう扱うか（行のない写真は消す、写真のない行は名前を外す）を確かめておく
- 一度も戻してみていないバックアップは、戻せるかどうか分からない

## 影響
- 消したデータも、書き出しには最長 5 週間残る。ポリシーにそう書く（0039）
- 費用は月に数十〜百数十円（書き出しの保存と、訓練の数時間分のインスタンス）
