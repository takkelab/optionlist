# 0019 「やりたいこと｜やったこと」を押したら、一覧を左右に滑らせて入れ替える

- 日付: 2026-11-03
- 状態: 確定（速さは触って調整する）
- 対象: screens.md §1、SPEC.md（版）

## 決めたこと
- ヘッダーの切り替えを押したら、一覧が画面の幅いっぱいに左右に滑って入れ替わる（0.25 秒、動き出しも止まりもなめらかな曲線）。やったことへは左へ抜けて右から入り、やりたいことへはその逆。ヘッダー・タブバーは動かさず、選んでいる側の白い印（背景だけ）は文字の下を滑って移る
- 右下の「＋」は一覧と一緒に滑らせず、その場で薄くなって消え・出る
- 切り替えはタップだけのまま（左右スワイプは入れない。0012 は変えない）
- 視差効果を減らす設定と、View Transitions が使えないブラウザでは、今までどおりすぐ切り替える

## 理由
- ユーザーの要望。切り替えの並び（左がやりたいこと、右がやったこと）と同じ向きに動くと、2 つのリストが横に並んでいる感じが伝わり、パッと替わるより「同じ画面の中の切り替え」（0012）に合う
- ブラウザの View Transitions を使った。前後の見た目を撮って CSS で動かすので、ルートや一覧の作りを変えずに済む（Motion で 2 つの画面を同時に描くより小さい）。iPhone の Safari は iOS 18 から使える
- React Router の `viewTransition` 指定は `RouterProvider`（データルーター）でしか効かず、このアプリの `<BrowserRouter>` では効かないので、`document.startViewTransition` を自分で呼ぶ（`lib/PageSlide.ts`）
- `<BrowserRouter>` は画面の切り替えを `startTransition` で包むので、`flushSync` でも描き終わらず、前の画面を「切り替えた後」として撮ることがある。`useTransitions={false}` にして切り替えをすぐ描く。このアプリは画面を遅れて読み込む作り（lazy・Suspense）を使っておらず、包む利点がない

## 影響
- `StatusSwitch` が押されたときに `PageSlide` で切り替える。向きは `<html>` の `data-switch-to` で global.css に渡す
- ヘッダー・タブバー・「＋」・選んでいる側の印に `view-transition-name` を付けた。トークンに `--motion-switch` を足した
- 切り替えた先の一覧は画面を開いてから読み込むので、そのまま撮るとカードのない一覧が滑ってきて、カードは後からパッと出る（ユーザーが実機で気づいた）。View Transitions は切り替えの処理（update）が返す Promise が終わるまで後の見た目を撮らないので、一覧の読み込みが終わる（`CollapsingList` の `data-list-ready` が出る）まで待ってから撮る。待つのは最長 0.3 秒で、遅いときは待たずに滑らせる（カードは後から出る）。切り替えの間は描画が止まって requestAnimationFrame が呼ばれないので、MutationObserver で待つ。読み込んだ一覧を覚えておく形（初回は同じ問題が残る）や、2 つの一覧を横に並べて常に描く形（作りが大きく変わる）は採らなかった
- 待つ分だけ「押してから動き出すまでに引っかかる」とユーザーが感じたので、切り替えに指が触れた瞬間（pointerdown。離す前）に先の一覧を読み始め、開いた画面がそれを使う（`lib/ListPrefetch.ts`）。タップの間（約 0.1 秒）に読み込みが進む。先読みは 2 秒の間だけ使い、1 回で捨てない（開発中の StrictMode は画面を開くときの読み込みを 2 回走らせるので、使い切りだと 2 回目が読み直しになる）
- はじめは一覧を全幅で滑らせたが、ユーザーから「一瞬カードが消える」と声があった。切り替え中の画面をコマ撮りすると、左から入るときは各カードの右側（文字のない側）だけが見えて、空のカードが滑ってくるように見えていた。そこで「30px ずれながら薄く入れ替わる形（Material Design の shared axis）」と「全幅のまま遅くした形」を作り、ユーザーが実機で並べて比べた。全幅を 0.35 → 0.3 → 0.25 秒と速めたところ、全幅・0.25 秒がいちばん良いとなった（速いと、文字のない側が見える時間も短い）
- 選んでいる側の印は、はじめは選んでいる側のリンクを文字ごと動かしていたので、前後の文字が重なって二重に見えた。印を背景だけの部品にし、文字は別に撮って印の上に重ねる。印はどちらの画面でも文字より前に 1 つだけ置く（動いている間の重なりの順は前の画面の並びで決まるので、リンクの中に置くと、前の画面で文字より後ろにあった印が文字を隠す）
- それでも「押してから動き出すまでのラグ」が残ったので、2 つ足した（ユーザーと相談のうえ）
  - 動きの曲線を、押した瞬間から速く動いて最後にゆっくり止まる曲線（decelerate）にした。動き出しも止まりもなめらかな曲線では、最初の数コマがほとんど動かず、間があるように感じる
  - 画面を開いたときにもう片方の一覧も裏で読み、最近読んだ一覧として覚えておく。切り替えた先の画面はそれをすぐ出し（読み込みを待たずに滑らせる）、指が触れたときの読み直しが届いたら置き換える。画面で書き換えた一覧も覚え、別の一覧へ項目を移したときは、移した先の覚えている一覧を捨てる（古い中身を出さず、そのときだけ読み込みを待つ）。覚えた一覧を出すのは 60 秒まで（`useStatusList`、`lib/ListPrefetch.ts`、`lib/ListMerge.ts`）
  - 負荷: 一覧の読み込みは切り替え 1 回で 1 回から 2 回になる。一覧の API は性能用のデータ（項目 1,000 件）でも p95 約 29ms（目標 50ms）で、1 人で使う分には問題ない
  - 指が触れた瞬間（離す前）に切り替える形は採らない。ヘッダーの上からスクロールし始めただけで切り替わってしまう
- 開発用のサーバー（`dev:lan`）は React の確認処理が多く、スマホでは切り替えた後の画面を描く処理が本番より遅い。動き出しの速さは本番用のビルド（`build` → `preview --host`）で確かめる
- E2E: 切り替えで滑る動きが流れること、視差効果を減らす設定では流れないこと（navigation.spec.ts）
